# Бэкап базы на Яндекс.Диск

Ежедневный дамп MySQL уезжает в облако, на почту приходит отчёт. Смысл в том,
чтобы данные пережили смерть сервера, поэтому копия хранится **вне** его диска.

| Файл | Что делает |
|---|---|
| [`backup.sh`](./backup.sh) | дамп → gzip → gpg → Яндекс.Диск → письмо → ротация |
| [`restore.sh`](./restore.sh) | скачать бэкап, проверить, при `--apply` залить в базу |
| [`get-token.sh`](./get-token.sh) | разово получить `refresh_token` (запускать на машине с браузером) |
| [`backup.conf.example`](./backup.conf.example) | пример конфигурации для `/etc/<app>-backup.conf` |

## 1. Приложение на oauth.yandex.ru

В настройках приложения укажите свой `client_id` и проверьте:

- Право **`cloud_api:disk.app_folder`** — доступ только к папке `Приложения/<имя>`.
  Берите именно его, а не `disk.write`: если сервер взломают, утёкший токен не
  откроет остальной Диск.
- Redirect URI: `https://oauth.yandex.ru/verification_code`.

Дальше на своём Mac:

```bash
./get-token.sh <client_id> <client_secret>
```

Скрипт откроет ссылку для подтверждения, обменяет код на токены и напечатает
готовые строки для конфига.

Альтернатива без браузера на нужной машине — device flow: запросить код у
`https://oauth.yandex.ru/device/code`, ввести показанный `user_code` на
https://ya.ru/device, затем обменять `device_code` на токены через
`/token` с `grant_type=device_code`. Именно так был выдан текущий токен. `refresh_token` бессрочный — `backup.sh` меняет по
нему короткоживущий access-токен на каждом запуске и записывает новый refresh
обратно в конфиг (Яндекс гасит старый при каждом обмене).

## 2. Пароль приложения для почты

Обычный пароль от ящика в SMTP не пройдёт. На
[id.yandex.ru/security/app-passwords](https://id.yandex.ru/security/app-passwords)
создайте пароль приложения для **Почты** и положите его в `SMTP_PASS`.

## 3. Установка на сервере

```bash
apt update && apt install -y curl jq gnupg mysql-client   # debian/ubuntu

mkdir -p /opt/app-backup
cp backup.sh restore.sh /opt/app-backup/
chmod +x /opt/app-backup/*.sh

cp backup.conf.example /etc/app-backup.conf
chown root:root /etc/app-backup.conf
chmod 600 /etc/app-backup.conf            # внутри токены и пароли
nano /etc/app-backup.conf                 # APP_DIR, секреты, GPG_PASSPHRASE
```

Пароль от базы скрипт читает из `$APP_DIR/.env` сам и передаёт mysqldump через
временный `--defaults-extra-file`, а не аргументом — аргументы видны в `ps`
любому пользователю системы.

**Пароль `GPG_PASSPHRASE` сохраните вне сервера** (менеджер паролей). В дампе
лежит вся переписка пользователей; без пароля бэкапы не восстановить, а с пустым
`GPG_PASSPHRASE` они уедут в облако открытым текстом.

Пробный запуск:

```bash
/opt/app-backup/backup.sh
```

Должно прийти письмо со списком загруженного и остатком места на Диске.

## 4. Расписание

```bash
crontab -e
```

```
30 3 * * * /opt/app-backup/backup.sh
```

Скрипт пишет в путь из `LOG_FILE` и сам шлёт письмо при провале,
поэтому вывод cron перенаправлять не нужно.

Отдельно заведите монитор на [healthchecks.io](https://healthchecks.io) и
пропишите его URL в `HEALTHCHECK_URL`. Это ловит случай, который скрипт не может
поймать по определению: сервер лежит и бэкап вообще не запускался — писем нет, и
без монитора это выглядит ровно как «всё хорошо».

## 5. Восстановление

```bash
/opt/app-backup/restore.sh --list              # что есть в облаке
/opt/app-backup/restore.sh                     # скачать последний и проверить
/opt/app-backup/restore.sh --apply             # залить в базу (спросит подтверждение)
```

Без `--apply` скрипт только скачивает, расшифровывает и проверяет дамп — так
можно раз в месяц убеждаться, что бэкапы рабочие, ничего не ломая.

Полное восстановление с нуля:

```bash
restore.sh --file env-2026-09-10-0330.txt.gz.gpg   # вернуть .env (в нём APP_KEY)
restore.sh --apply                                  # вернуть базу
php artisan config:clear && php artisan migrate
```

Без `APP_KEY` из старого `.env` зашифрованные поля и сессии не расшифруются, даже
если база восстановлена полностью.

## Вложения

`storage/app` архивируется раз в неделю (`BACKUP_STORAGE=1`, `STORAGE_WEEKDAY=7`)
в `storage-<дата>.tar.gz.gpg`, **но только файлы не крупнее `STORAGE_MAX_FILE_MB`
(25 МБ)**. Порог совпадает с `uploads.encrypt_max_bytes`: приложение шифрует на
диске ровно то, что попадает в бэкап.

На сентябрь 2026 это 210 файлов и 93 МБ вместо 337 МБ — три крупных файла
(видео и два установщика, 242 МБ) дают три четверти веса. **Они не бэкапятся:
при потере сервера их не вернуть**, копируйте отдельно, если они важны. Каждое
письмо-отчёт называет, сколько файлов и мегабайт осталось за бортом.

tar снимается с живого каталога, поэтому `file changed as we read it` не считается
ошибкой: это гонка с приложением, а не порча архива. Целостность проверяется
через `tar tzf` после сборки.

Когда вложения перерастут квоту, есть два пути:

1. **Хранить сразу в S3.** В [config/filesystems.php](../../config/filesystems.php)
   диск `s3` уже настроен, в `.env` стоит `FILESYSTEM_DISK=local`. Переключение
   снимает вопрос бэкапа файлов совсем.
2. **Инкрементальный синк** через `rclone sync` — гоняются только изменившиеся файлы.

## Проверка восстановления

Периодически выполняйте восстановление в изолированную тестовую среду и
сверяйте количество таблиц, записей и доступность вложений. Не используйте
боевую конфигурацию или production-базу для такой проверки.
